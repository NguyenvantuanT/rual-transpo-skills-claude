# ARCHITECTURE

> Architecture overview for the **Rual Transpo** mobile project. This codebase produces **two separate iOS/Android apps** from a single Flutter project — a **Rider app** (driver/delivery) and a **User app** (customer).

## TL;DR

| Aspect | Value |
|---|---|
| **Apps built** | 2 — `Rider` + `User` |
| **Environments per app** | 3 — `development`, `staging`, `production` |
| **Total flavor combos** | 6 |
| **Flutter version** | 3.44.0 (pinned via FVM, see `.fvmrc`) |
| **Locale default** | `fr` (French) — France market |
| **Architecture** | MVVM (`Page` + `ViewModel`), Provider, GetIt, auto_route |
| **Networking** | Dio (single instance, interceptors) |

### How the two apps differ

| | Rider | User |
|---|---|---|
| **Entry point** | `lib/app/main_rider_dev.dart` | `lib/app/main_user_dev.dart` |
| **Root widget** | `lib/rual_transpo_rider_app.dart` | `lib/rual_transpo_user_app.dart` |
| **Initial route** | `SplashRiderPage` | `SplashUserPage` |
| **Router (DI)** | `AppRouter` | `AppRouterUser` |
| **`AppConfig.isRider`** | `true` | `false` |
| **App name (dev)** | "Rual transpo rider dev" | "Rual transpo driver dev" |
| **Shared** | ✅ Theme, models, services, base VM, components, l10n | ✅ same |

The split is driven by **one flag** — `AppConfig.shared.isRider` — set during `AppConfig.create(...)` in the entry point. Everything else (DI registration, root widget) branches off that flag.

## 2. Build flavors and schemes

Each app supports 3 environments → **6 flavor combinations total**, named with **camelCase, app-type suffix**:

| Flavor | App | Build config | Scheme | Entry point | Env file |
|---|---|---|---|---|---|
| `developmentRider` | Rider | `Debug-developmentRider` | `developmentRider` | `main_rider_dev.dart` | `.env.dev` |
| `stagingRider` | Rider | `Debug-stagingRider` | `stagingRider` | *(not yet)* `main_rider_stg.dart` | `.env.stg` |
| `productionRider` | Rider | `Debug-productionRider` | `productionRider` | *(not yet)* `main_rider_prod.dart` | `.env.prod` |
| `developmentUser` | User | `Debug-developmentUser` | `developmentUser` | `main_user_dev.dart` | `.env.dev` |
| `stagingUser` | User | `Debug-stagingUser` | `stagingUser` | *(not yet)* `main_user_stg.dart` | `.env.stg` |
| `productionUser` | User | `Debug-productionUser` | `productionUser` | *(not yet)* `main_user_prod.dart` | `.env.prod` |

> **Naming convention** (load-bearing — do not change):
> - Flavor string = Scheme name = camelCase, no separator: `developmentRider`, `stagingUser`, …
> - Build config = `{Profile|Debug|Release}-{flavor}` (e.g. `Debug-developmentRider`)
> - Flutter's `--flavor` matches the scheme name **case-sensitively**, so `developmentRider` ≠ `development_rider` ≠ `development-rider`.

### How to run

```bash
# Rider dev (currently the only fully-wired entry point)
fvm flutter run \
  --flavor developmentRider \
  -t lib/app/main_rider_dev.dart \
  --dart-define-from-file=.env.dev

# User dev
fvm flutter run \
  --flavor developmentUser \
  -t lib/app/main_user_dev.dart \
  --dart-define-from-file=.env.dev
```

In VS Code, the `.vscode/launch.json` already has both `Development rider` and `Development user` configs — pick one in the Run sidebar.

## 3. Environment files

There are **four** `.env*` files at the project root (all four are currently tracked by git — `.gitignore` does not list them):

- `.env` — default/prod-like (MODE=prod), real `api-dev.xxx.fr` URL
- `.env.dev` — dev environment
- `.env.stg` — staging (`cme-api-stg.tekup.vn`)
- `.env.prod` — production (`api.cmemanager.vn`)

The app reads API base URLs, socket URLs, Google API keys, RevenueCat keys, and Appsflyer key via `flutter_dotenv`. When adding new env vars, also update `pubspec.yaml`'s `flutter.assets` list (and the `flutter_gen.exclude` block).

## 5. MVVM pattern (enforced by base classes)

- **Page** extends `StatelessWidget` (or `StatefulWidget`) and mixes in `MixinBasePage<MyVm>`. The mixin wires up a `ChangeNotifierProvider`, dispatches loading/snackbar callbacks to view-model hooks, and renders one of five `ChangeState` views (`loading` / `blank` / `page` / `serverError` / `clone`).
- **ViewModel** extends `BaseViewModel` (which extends `ChangeNotifier`). Override `onInit()`; optionally `onAppear()` / `onDisAppear()` (declared `external` in the base class). Call `showLoading()` / `hideLoading()`, `changeState(ChangeState.serverError)`, `showError(message)`, `showErrorConnection()`, etc. instead of touching UI directly.
- ViewModels access `api` (Dio), `prefs` (SharedPrefs), and `appRouter` from the base class — they're all `locator<...>()`-backed singletons.

### Page + VM co-location

- `pages/<feature>/<feature>_page.dart` + `pages/<feature>/<feature>_vm.dart`
- Page name is `<Feature>Page`, VM is `<Feature>Vm`

For app-specific features, the folder is `pages/<feature>_<app>/` — e.g. `splash_rider/splash_rider_page.dart` and `splash_user/splash_user_vm.dart`.

## 6. Dependency injection (`src/utils/locator.dart`)

`GetIt` singleton named `locator`. The DI registration **branches on `isRider`** so the right router is injected for the right app:

```dart
void setUpInjector({required bool isRider}) {
  locator.registerLazySingleton(() => SharedPrefs());
  locator.registerLazySingleton(() => ApiClient());
  locator.registerLazySingleton<AppRouterBase>(
    () => isRider ? AppRouter() : AppRouterUser(),
  );
}
```

Call `locator<...>()` anywhere (do not pass through constructors unless the type is naturally testable in isolation).

## 7. Routing (`router/app_router.dart`)

Uses `auto_route`. Two routers:

- `router/app_router.dart` → `AppRouter` — **Rider** routes (`SplashRiderPage`, `MainRiderPage`, …)
- `router/app_router_user.dart` → `AppRouterUser` — **User** routes (`SplashUserPage`, `MainUserPage`, …)
- `router/app_router_base.dart` → abstract `AppRouterBase` — common interface, used as the locator type

To add a route: add it to the relevant `routes` list, annotate the page with `@RoutePage()`, then run `fvm flutter pub run build_runner build --delete-conflicting-outputs`. Generated file `app_router.gr.dart` — never edit by hand.

## 8. Theming

`AppTheme` exposes `lightTheme` and `darkTheme`. The active theme uses two `ThemeExtension`s:

- `AppColorScheme` — semantic colors (`primaryText`, `divider`, `shadow`, `disabled`, `success`, `error`, etc.). Access via `context.appColor.<token>` (extension is defined next to `app_color_scheme.dart`).
- `AppStyleScheme` — typographic scale (`display36Bold` … `display10Regular`, two weights per size). Access via `context.appStyle.<token>`.

Both light and dark themes register both extensions; the dark variants re-color styles to `AppColor.white`. The `AppThemeMode` enum currently has a third value `kimia` declared but unused.

---

## 9. Localization

`pubspec.yaml` sets `flutter_intl.enabled = true` with `main_locale: fr`, `arb_dir: lib/src/l10n`, output to `lib/src/generated`. Currently only French (`intl_fr.arb`) and English (`intl_en.arb`) exist. Use `S.current.<key>` (from `package:rual_transpo_rider_mobile/src/generated/l10n.dart`). When adding a key, add it to both ARB files and run `intl_utils:generate`.

---

## 10. Persistence (`services/local/share_prefs.dart`)

Token and user model are stored via `flutter_secure_storage` (with one-time migration from `shared_preferences` on first launch). Theme mode and locale code live in `shared_preferences`. `SharedPrefs.initialise()` is called from `main()` after `setUpInjector()`.

---

## 11. Networking (`services/remote/api_client.dart` + `api_interceptor.dart`)

Single `Dio` instance. `ApiInterceptor.onRequest` injects `Authorization: Bearer <token>` (skipped for `/auth/refresh`) and `language: <localeCode>`. `onError` short-circuits to a "no internet" `DioException` when connectivity is `none`, and otherwise extracts the API's `code` or `message` field. HTTP client in non-release mode accepts self-signed certs. `pretty_dio_logger` is attached in debug mode.

## 12. Conventions

- **Page + VM co-location** — `pages/<feature>/<feature>_page.dart` + `pages/<feature>/<feature>_vm.dart`. Page name is `<Feature>Page`, VM is `<Feature>Vm`.
- **App-specific folders** — suffix `_rider` or `_user` (e.g. `splash_rider/`, `main_user/`).
- **Generated asset paths** — never use string paths to `assets/icons/foo.svg`; use `AppAsset.icons.foo.path` (regenerated by `flutter_gen`).
- **Generated font family** — use `FontFamily.roboto` constant, not the string `'Roboto'`.
- **Constants in `AppConstants`** — read `AppConfig.shared.*` at static init time; default-locale/country/phone-mask constants live there too (`defaultLang = 'fr'`, `phoneCode = '+33'`, `countryCode = 'FR'`, `phoneMask = '0 00 00 00 00 00'`).
- **Per-feature folders under `components/`** (`button/`, `loading/`, `snack_bar/`) — group new shared widgets the same way.
- **Error visibility** — every page reaches `serverError` state via `changeState(ChangeState.serverError)`. `ServerError` widget currently renders only a centered loader (intentionally a stub).
- **Flavor strings are case-sensitive** — `developmentRider` ≠ `development_rider` ≠ `development-rider`. The scheme name, the `--flavor` value, and the build configuration name (Debug-{flavor}) must all match exactly.
